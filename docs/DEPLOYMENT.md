## 0. 먼저 정해야 할 것

배포 전에 결정이 필요한 항목입니다. 코드로 해결되지 않습니다.

| 항목 | 왜 필요한가 |
| --- | --- |
| **개인정보 수집·이용 동의 문구** | 이름·연락처·학교를 받으므로 법적으로 필요합니다. **아직 만들지 않았습니다** |
| **데이터 보관 기간** | 행사 후 언제 지울지. 동의 문구에 명시해야 합니다 |
| **문의 창구** | 조회가 안 되는 참가자가 연락할 곳 |
| **멘토 모집 시작일** | 아래 "순서" 참고 — 멘티보다 먼저여야 합니다 |

## 1. 오픈 순서: 멘토 먼저, 멘티 나중

**이건 취향이 아니라 기능적 제약입니다.**

매칭은 신청 시점의 멘토 명단에서 계산됩니다. 멘토가 없는 상태에서 멘티가 신청하면
결과 화면에 **"0명을 찾았어요"** 가 뜹니다. 첫인상이 그것으로 굳습니다.

```
멘토 모집 오픈  ─────────────────▶  (최소 1주)  ─────▶  멘티 오픈
   대학생 1,000명                   명단이 쌓임        고3 300명
```

부수 효과로 부하도 분산됩니다. 대학생 1,000명이 단톡방 공지로 한 번에 몰려도
그때는 멘티가 없어 매칭 계산이 돌지 않습니다.

## 2. 배포 절차

### 2-1. 사전 준비

- [ ] Supabase 키 재발급 (개발 중 쓰던 키는 폐기)
- [ ] 운영자 비밀번호를 운영용으로 새로 생성 (`openssl rand -base64 24`)
- [ ] `supabase/schema.sql` 이 운영 DB에 적용되어 있는지 확인
- [ ] 개발 중 쌓인 테스트 데이터 삭제 확인 (`users` 0행)

### 2-2. Vercel 배포

```bash
npx vercel --prod
```

GitHub 저장소를 연결하면 푸시할 때마다 자동 배포됩니다.

**환경변수는 Vercel 대시보드에 직접 넣습니다.** `.env.local` 은 올라가지 않습니다.
Project Settings → Environment Variables 에 아래를 Production 으로 추가:

| 이름 | 비고 |
| --- | --- |
| `SUPABASE_URL` | |
| `SUPABASE_SERVICE_ROLE_KEY` | **절대 `NEXT_PUBLIC_` 접두사 금지** |
| `ADMIN_PASSWORD` | 운영용 새 값 |
| `ADMIN_SESSION_SECRET` | 위와 다른 값 |

### 2-3. 배포 직후 확인 (실기기 필수)

브라우저 개발자도구가 아니라 **실제 폰**으로 해야 하는 것들입니다.
지금까지의 검증은 전부 데스크톱 시뮬레이션이라 아래는 한 번도 확인되지 않았습니다.

- [ ] iPhone Safari / Android Chrome 양쪽에서 신청 완주
- [ ] **사진 "찍기"** — 카메라가 실제로 열리는가 (`capture="user"`)
- [ ] **사진 "고르기"** — 실제 사진(2~5MB)을 올렸을 때 400KB 제한에 걸리지 않는가
- [ ] **참여코드 복사** — 클립보드 API는 HTTPS에서만 동작. 배포 후 처음 확인됨
- [ ] 키보드가 올라올 때 입력창이 가려지지 않는가
- [ ] 하단 CTA가 홈 인디케이터에 가리지 않는가
- [ ] 매칭 결과의 `tel:` 링크로 실제 전화 앱이 열리는가

## 3. 검증 일정

| 시점 | 할 일 | 소요 |
| --- | --- | --- |
| **D-21** | 배포 + 실기기 점검 (위 2-3) | 1~2일 |
| **D-19** | 운영진 10~20명 리허설. 실제로 신청서를 채워봄 | 2일 |
| **D-17** | 리허설에서 나온 문구·흐름 수정 | 2~3일 |
| **D-14** | **멘토 모집 오픈** ← 실사용 첫 데이터 | |
| **D-7** | 멘토 데이터를 보고 조정 (영역 분포, 캠퍼스 편중, 미매칭 예상) | 2~3일 |
| **D-3** | 최종 점검. 이 시점 이후로는 코드를 건드리지 않음 | 1일 |
| **D-0** | **멘티 오픈** | |

**최소 2주, 여유 있게 3주**를 권합니다.

### 왜 2주인가

- **실기기 문제는 하루 안에 다 안 나옵니다.** 기종·OS 버전마다 다르고, 특히 카메라와
  클립보드는 실제 사용자가 써봐야 드러납니다
- **리허설과 수정 사이에 하루는 비어야 합니다.** 리허설 당일에 고치면 급하게 짠 코드가
  다음 문제를 만듭니다
- **멘토 데이터가 쌓인 뒤 조정할 시간이 필요합니다.** 실제로 어떤 캠퍼스·영역에 멘토가
  몰리는지는 받아봐야 압니다. 특정 캠퍼스에 멘토가 없으면 그 캠퍼스를 지망한 멘티가
  전부 "0명"을 보게 됩니다

### 최소한으로 줄인다면

일정이 촉박하면 **1주**까지 줄일 수 있지만 아래는 포기할 수 없습니다:

1. 실기기 점검 (반나절)
2. 운영진 리허설 (1일)
3. 멘토 모집을 멘티보다 최소 3일 먼저 열기

리허설을 건너뛰는 것이 가장 위험합니다. 지금까지의 검증은 전부 제가 짠 시나리오라,
**실제 사람이 무엇을 헷갈려 하는지는 아직 아무도 모릅니다.**

## 4. 오픈 직후 지켜볼 것

첫 몇 시간이 가장 위험합니다. 운영자 화면(`/admin`)에서 확인:

| 신호 | 의미 | 대응 |
| --- | --- | --- |
| **미매칭 인원 증가** | 특정 캠퍼스에 멘토가 없음 | 그 캠퍼스 멘토 추가 모집 |
| 신청 수가 예상보다 적음 | QR·링크 전달 실패 가능성 | 전달 경로 확인 |
| 같은 사람이 여러 번 신청 | 완료 화면을 못 봤을 가능성 | 중복 행 정리 |
| 적합도가 전반적으로 낮음 | 가중치 조정 필요 | `WEIGHTS` 수정 후 재배포 |

**속도 제한 주의** — 현재 속도 제한은 서버 인스턴스 메모리에 기록됩니다.
Vercel 서버리스는 인스턴스가 여러 개라 인스턴스마다 따로 셉니다. 실제 제한이
설정값보다 느슨하게 걸립니다. 남용이 보이면 Upstash Redis 같은 공유 저장소로
옮겨야 합니다.

## 5. 아직 없는 것

배포 전에 만들지, 없이 갈지 결정해야 합니다.

| 항목 | 없으면 생기는 일 |
| --- | --- |
| **개인정보 수집 동의** | 법적 문제. 실제 오픈 전에 반드시 필요 |
| **데이터 파기 절차** | 행사 후 개인정보가 계속 남음 |
| 운영자 "전체 매칭 실행" | 결과를 안 본 멘티는 운영자 표에 안 나옴 |
| 중복 신청 방지 | 같은 사람이 여러 번 신청 가능 (연락처 중복 허용 상태) |
| 구글 시트 연동 | 운영자가 시트에서 못 봄 |
| 사진 저장소 | 현재 data URL로 DB에 직접 저장. 1,300명이면 용량 부담 |

## 6. 롤백

문제가 생기면 Vercel 대시보드 → Deployments → 이전 배포의 **Promote to Production**.
1분 안에 되돌아갑니다. DB 스키마를 바꾸지 않았다면 데이터는 그대로입니다.

**스키마를 바꾸는 배포는 되돌리기 어렵습니다.** 컬럼 추가는 안전하지만 삭제·변경은
오픈 기간 중에는 피하세요.
